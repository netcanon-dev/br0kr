# br0kr Security & Correctness Review — Final Synthesis

**Target:** `netcanon-dev/br0kr` · Postgres-backed Proxmox capacity broker
**Crown-jewel invariant under test:** *no concurrent double-allocation*
**Methodology:** 8 risk-ranked lenses → one reviewer per lens → dedup to 25 unique findings → adversarial verification by 1–2 independent refuters each (2 on every high/medium), instructed to refute by default. **Result: 0 refuted, 24 CONFIRMED, 1 PARTIAL (S12, impact downgraded). Tally: 2 high · 7 medium · 11 low · 5 info.**

---

## 1. Executive summary

**The crown-jewel invariant holds in the shipped, default configuration.** The admission floor's actual machinery — ordered per-scope `pg_advisory_xact_lock`, derived (not stored) capacity, guarded-CAS lifecycle, the 0004 per-cluster vmid unique index, single leader-writer — was attacked directly and survived; the two highest-severity findings both live *outside* the default hot path (an opt-in migration saga and a teardown timing window), not inside `admit()` itself. The real exposure is that two load-bearing preconditions of the floor are **assumed but never enforced in code**: `READ COMMITTED` isolation (S06) and a non-autocommit connection (S11). Neither fires in the shipped compose stack, but each *silently and totally* reopens the double-allocation race the moment the environment drifts — S06 on a Postgres whose `default_transaction_isolation` is `repeatable read`, S11 the day any new caller hands `admit()` an autocommit connection. **The single most important thing to fix is S06** — pin the isolation level at the `db.connect()` seam and assert it at startup — because it is the cheapest possible guard on the always-on admission path and converts the entire race-freedom proof from "true if the DBA cooperates" to "true by construction." The two `high`s (S01 double-migrate, S02 stale-destroyer) are genuine double-allocation / wrong-destroy paths but both sit behind qualifiers: S01 requires the default-OFF migration feature enabled, S02 requires an HA leadership drop mid-teardown. Everything from `low` down is operational-correctness, error-taxonomy, and hardening/doc-honesty debt — real, cheap, but not floor-threatening.

## 2. The admission floor verdict (the crown jewel)

**In the shipped default config the floor is sound.** Every debited scope is locked in canonical sorted order on a non-autocommit `READ COMMITTED` connection before the capacity re-read; capacity is derived as `limit − Σ active`; the last-slot loser re-reads under the lock and is rejected; idempotency is checked before capacity; and the vmid double-stamp is refused by the 0004 index. The refuters could not break it head-on. What they found instead are **two latent holes where a documented assumption is never asserted** — cheap to close, catastrophic if they ever open:

- **S06 — isolation is assumed, never pinned (`db.py:110`, medium).** `connect()` returns `psycopg.connect(dsn, autocommit=…, **opts)` inheriting the server's `default_transaction_isolation`. The whole proof needs `READ COMMITTED` so the post-lock capacity re-read sees a competitor that committed *while this txn waited on the advisory lock*. Under `REPEATABLE READ`, each txn's snapshot is frozen at its first statement (the `pg_advisory_xact_lock` call itself, *before* the lock wait), so the winner's committed lease is invisible to the loser's re-read; with no SSI to abort it, both `INSERT` and commit. **Silent, total, zero log lines** — and it fires only on a non-default server config, which is exactly the kind of drift a managed-DB parameter group or a hand-tuned `postgresql.conf` introduces without anyone touching br0kr.

- **S11 — `admit()` lacks the non-autocommit guard its siblings enforce (`admission.py:403`, low).** `promote_pinned` (648-652) and `run_migration_step` (459-464) both `raise RuntimeError` on an autocommit connection, because there `pg_advisory_xact_lock` releases at statement end and the lock no longer spans read+insert. `admit()` — the *primary* race-critical seam with the identical requirement — has no such check. Every current caller passes non-autocommit (verified), so this is latent; it trips the day a new daemon step, admin verb, or harness calls `admit(work_conn, …)` with the tick's autocommit work connection. The floor's most important function is the only one relying purely on caller discipline.

- **S21 — hashtext docstring is benign (`admission.py:424`, info).** The inline "harmless: can only over-serialize, never MISS an exclusion" is correct on exclusion. The only imprecision: a cross-paired 32-bit collision could invert *lock-acquisition order* between two txns → a Postgres-detected deadlock → one txn aborts as an uncaught psycopg error → a transient 5xx. Never a double-allocation (probability effectively zero; requires two crosswise `2⁻³²` collisions co-held). Docs-only.

**Framing:** S06 and S11 are not "the floor is broken" — they are *the two places where a true invariant is enforced by prose and convention rather than by an assertion.* Both fixes are a handful of lines and they upgrade the crown jewel from a load-bearing **assumption** to a machine-**enforced** invariant. Do them first.

## 3. Findings by theme

### Admission floor & concurrency
- **[S06] Isolation assumed, never pinned** — medium, `db.py:110`. The race-freedom proof requires READ COMMITTED; nothing sets/asserts it, so a `repeatable read` ledger silently reopens the last-slot race. *Repro:* point `PGCONN` at a Postgres with `default_transaction_isolation='repeatable read'`; race two agents for the last slot on a node → both admitted. *Fix:* set `conn.isolation_level = READ_COMMITTED` in `connect()` (or `-c default_transaction_isolation=read committed` in `KEEPALIVE`) + a `SHOW transaction_isolation` startup assertion that refuses to serve otherwise.
- **[S11] `admit()` missing the non-autocommit guard** — low, `admission.py:403`. Its two siblings raise on autocommit; `admit()` doesn't, so a future autocommit caller releases the scope lock per-statement and re-enables double-allocation. *Repro:* call `admit(work_conn, …)` on the tick's autocommit connection; two last-slot admits both pass `shortfall` and INSERT. *Fix (one-liner):* `if getattr(conn,'autocommit',False): raise RuntimeError(...)` at the top of `admit()`, mirroring `run_migration_step`.
- **[S21] hashtext docstring slightly overstates** — info, `admission.py:424`. A cross-paired collision inverts lock order → detectable deadlock, never a missed exclusion. *Fix:* amend the comment to "…never a missed exclusion; at worst an over-serialization or an aborted (detected) deadlock."

### Cross-cluster migration saga & idempotency *(all behind the default-OFF `BR0KR_MIGRATE_LIMIT=0` path; PDM contract unverified)*
- **[S01] Double-migrate strands a running, undebited guest on the target** — **high**, `migration.py:543`. No one-active-saga-per-lease constraint + `_actuate` never checks `facts.lease_node` vs `mig.source_node`, so a second saga physically moves the guest off its *current* node, then the flip's CAS (guarded on the stale recorded source) reports "lost" → ABORT+settle → guest runs on the target fenced to a LIVE lease, undebited; a later `admit()` on that node over-commits. *Repro:* `migrate(L→B)`, let it finish, then `migrate(L→C)` with a fresh idem_key. *Fix:* partial unique index on `migration(lease_id) WHERE state IN (REQUESTED,RESERVED,MIGRATING)` → map to `migration_in_progress`; abort `source_changed` when `facts.lease_node != mig.source_node` *before* actuating (or CAS the flip against `facts.lease_node`).
- **[S07] Resumed/overlapping actuation aborts+settles while the copy still lands** — medium, `migration.py:556`. The remote-migrate task UPID is never persisted, so a resume after `migrate_timeout` (300s budget < a real cross-cluster copy), crash, or the ~one-tick leader overlap re-POSTs the migrate or trusts a laggy inventory read; `plan()` maps `migrate_failed`/`gone` to a terminal abort that settles the target reservation while the server-side copy is still in flight → target over-commit + a lease stranded on the source. *Fix:* persist the UPID and re-attach (`pdm.wait`) on resume instead of re-POSTing; treat `gone` as retry while `MIGRATING`; settle only on confirmed source-present-unlocked or confirmed task-failure.
- **[S10] enqueue ON CONFLICT loser reports a different ask as queued** — low, `admission.py:617`. The re-read path returns `queued=True` without the same-ask check the sequential pre-check and `admit()`'s row-None path apply, so two concurrent `queue=true` calls sharing an idem_key with different asks silently coerce the loser onto the winner's ask. *Fix:* run the inline same-ask comparison against the re-read row in the row-None branch (and `lease_not_live` for terminal). *(Corroborated independently by the admission-floor lens.)*
- **[S25] `_find_on_target` treats fence-visible-in-cluster as proof-of-arrival** — info, `migration.py:534`. If an operator repoints the target node's `cluster_id` into the lease's own cluster mid-saga, the SOURCE guest satisfies the commit fast-path → flip+settle with no move → capacity misattributed. Speculative trigger. *Fix:* abort/retry when `facts.source_remote == facts.target_remote` before honoring a dest-present read; match on the target node, not just the cluster.

### VM teardown, fencing & orphan reclaim
- **[S02] `fenced_destroy` has an unbounded check-to-act gap** — **high**, `pve.py:295`. The fence tag is read once, then an *unfenced* `_stop_best_effort` (up to 60s+ task wait) runs before the DELETE with no tag re-read, so a stalled destroyer that outlives the reap grace (default 30s, min 0) can, after leadership fails over and the vmid is reused, stop+delete a *different* live lease's guest — the exact wrong-destroy the fence exists to prevent, logged as success. *Repro:* leader A stalls inside the stop; standby B re-hands the lease after grace, provisions a new lease onto the reused vmid; A resumes and deletes it. *Fix:* re-read tags immediately before the DELETE and refuse on mismatch (shrinks the window to one round-trip); raise the default grace above the internal stop+delete budget; fence the stop. *(SECURITY.md C8's absolute "cannot destroy a reused vmid's guest" is falsified by this window.)*
- **[S04] `_reclaim_builds` marks a build FAILED before the guest is confirmed destroyed** — medium, `daemon.py:711`. Terminal-first + a single destroy attempt: one raise (transient PVE error / node reboot / still-locked import task) or a silent driver-None skip permanently orphans the build VM — `stale_builds` excludes terminal rows, and the `br0kr-build-<id>` fence matches neither sweep phase, so no automation ever reclaims it. *Repro:* leader dies mid-import; reclaim runs after `build_stale_seconds`; destroy raises. *Fix:* invert to destroy-first, `mark_failed` only on a definitive verdict; leave non-terminal on a raise so `stale_builds` retries; at minimum log the driver-None skip. Fix the two false docstrings (`reconciler._destroy_build`, the import_timeout comment).
- **[S08] All three destroyers ignore the DELETE task exitstatus** — medium, `pve.py:298`. `fenced_destroy`/`destroy_clone_orphan`/`destroy_build_vm` capture `rc = wait(upid)` but return `'destroyed'` unconditionally, so an async-failed or timed-out delete is reported as success → `mark_released` frees derived capacity while the guest still runs (node over-committed) — and for builds it compounds S04 into a permanent orphan. *Repro:* storage cannot remove the disk; the DELETE task fails server-side. *Fix:* branch on `rc`; raise on non-OK for the reaper's retry path; treat `TIMEOUT` like the create TIMEOUT (leave the claim for next grace). Every *other* driver verb already checks its task rc.
- **[S20] Mass-absent breaker only guards ALL-absent scans** — low, `sweeper.py:182`. A partially-stale ledger (restored backup or promoted lagging standby) still contains older lease rows, so `orphans != scanned` and the breaker never trips — the sweep destroys every live guest created *after* the restore point. The docstring over-claims "a lagging replica" as guarded. *Fix:* refuse when the absent fraction exceeds a threshold, or require absent-lease ids below the ledger's `max(lease.id)` watermark (an id at/above it is positive rollback evidence); at minimum correct the docstring/SECURITY.md C10 and add a `sweep_dry_run`-first DR runbook note.

### Input validation & error taxonomy
- **[S03] Agent ttl/max_wait/huge-int escape as uncaught DB errors** — medium, `admission.py:508`. `validate()` never bounds `ttl_seconds`/`max_wait_seconds`/integer ranges and the INSERT try/except catches only `ForeignKeyViolation`, so `ttl_seconds=5` (CHECK ≥10), `>2³¹` (int4), `max_wait≈1e13` (interval overflow), or `10**400` (OverflowError in `isfinite`) surface as a raw FastMCP error string instead of `{admitted:false, reason:…}`, breaking the documented reason contract the codebase itself declares load-bearing. *Repro:* `request_lease(ttl_seconds=5)` on a node with room. *Fix:* bound the values in `validate()` (mirror admin.py's `_INT_MAX`/`_BIGINT_MAX`), wrap `isfinite` for OverflowError; defense-in-depth: widen the except to map `CheckViolation`/`DataError` with rollback.
- **[S19] `validate_patch` has no upper bound on int knobs** — low, `settings.py:153`. A value above 2³¹−1 passes validation and fails at the UPDATE with `NumericValueOutOfRange` → opaque 503 instead of the promised crisp 400. *Repro:* POST `/api/settings/edit {"provision_limit":3000000000}`. *Fix (one-liner):* `if val > 2_147_483_647: return f'too_large:{key}'`. *(Corroborated independently by the audit/observability lens.)*
- **[S18] `apply_pending` finally masks the root cause** — low, `migrate.py:151`. The `finally` runs `pg_advisory_unlock` on a possibly-aborted txn, so the unlock raises `InFailedSqlTransaction` and supersedes the real error (e.g. an `InsufficientPrivilege` CREATE on a non-owner role becomes "current transaction is aborted"). *Fix:* `with suppress(Exception): conn.rollback(); conn.execute(unlock); conn.commit()` — the session lock releases with the session anyway.

### Dashboard & web surface
- **[S16] No security headers; JSON 404 reflects the raw path unescaped** — low, `dashboard.py:2233`. `_write` sends only Content-Type/Length — no CSP/X-Frame-Options/X-Content-Type-Options — and the 404 body echoes `self.path` with `json.dumps` leaving `<`/`>` intact. Real-world exploitability is limited (modern browsers won't MIME-sniff `application/json` on a navigation), but nosniff+CSP+frame-ancestors close it definitively and are absent; the blast radius is the unlocked operator token in `sessionStorage`. *Fix:* always send `nosniff` + `X-Frame-Options:DENY` + a strict CSP (`default-src 'none'; script-src/style-src 'unsafe-inline'`); return only `{"error":"not_found"}`.

### Health, liveness & the single-threaded tick
- **[S05] Readiness/liveness never degrade under persistent tick failure** — medium, `daemon.py:764`. Both probes consult only the loop-progress stamp, which `serve()` refreshes at the top of *every* iteration even when `tick()` raises, so a tick that raises on every pass keeps `/healthz` and `/readyz` green forever — nothing provisions/reaps/promotes while the orchestrator sees green and expired leases pin capacity fleet-wide. `serve()`'s own comment claims a degradation mechanism that does not exist. *Repro:* break a tick-owned statement (e.g. connection exhaustion on the per-tick promote connect) that spares the health scrape. *Fix:* publish a consecutive-failure counter / last-successful-tick monotonic into `HealthState` and make `readiness()` return `not_ready` after `N*interval`; at minimum correct the contradicting comment.
- **[S17] Leader probe has no application-level timeout** — low, `leader.py:92`. `still_leader()`/`try_acquire()` run a bare SELECT with no `statement_timeout`/`tcp_user_timeout`, so a blackhole partition blocks the probe for the OS TCP timeout (~60s common, up to ~15min tail) while `serve()` stops beating → `/healthz` 503 → an orchestrator kills a daemon that is correctly riding out a ledger outage, contradicting the "liveness is ledger-independent" intent. *Fix:* give the leader connection `-c statement_timeout=3000` (or `tcp_user_timeout`), so a blackholed probe raises in seconds and `run()` re-homes cleanly.
- **[S12] Audit prune is one unbatched, un-heartbeated DELETE** — low, **PARTIAL**, `audit.py:428`. `prune()` issues a single unbounded `DELETE` and the tick calls it with no `_beat()` around it — uniquely among the tick's slow steps — so a first-enablement prune of a large trail freezes reconciliation for the statement's duration and can flap `/healthz` unhealthy. **The catastrophic tail was refuted:** shipped Compose does *not* restart unhealthy containers (the runbook's "503 → Compose restarts it" is itself wrong), and even under k8s the orphaned backend runs the DELETE to completion and commits (client death doesn't cancel the statement), so the "self-sustaining crash loop / retention never completes" does **not** reproduce. **What remains:** a one-time multi-minute reconciliation freeze + unhealthy flap at first enablement on a multi-million-row backlog. Severity correctly downgraded to low. *Fix:* batch via `ctid IN (… LIMIT 10000)` calling `_beat()` between batches (or `SET LOCAL statement_timeout` and chip away across windows).

### HA / single-writer / deploy
- **[S09] DR replication posture is init-only** — medium, `docker/pg-primary-init.sh:44`. The trust-vs-scram decision runs only in `initdb`; converting a previously trust-initialised primary to stretched-DR publishes 5432 on the mesh IP while `host replication all all trust` remains in force — any host that can route to `PRIMARY_BIND:5432` can `pg_basebackup` the whole ledger as the `broker` superuser with no password, while the operator believes replication is scram+TLS-gated per the runbook. *Repro:* default `up -d`, later add `primary-remote.yml` on the existing volume. *Fix:* in `pg-primary-tls-entrypoint.sh` (runs every boot in DR mode) refuse to start / strip the line if a `replication … trust` rule is present, and idempotently ensure the scram `replicator` role + `hostssl scram-sha-256` rule + slot; loudly require a fresh volume when converting.
- **[S22] Ex-leader emits ledger-wide metrics until it re-stands-by** — info, `daemon.py:795`. On losing leadership `serve()` returns and `run()` `break`s to reconnect *before* publishing `ROLE_STANDBY`, so under `--scale daemon=2` a scrape during the reconnect window double-counts the leader-only gauges for a few seconds. Self-heals. *Fix (one-liner):* `_publish_health(ROLE_STANDBY, None)` immediately after `serve()` returns, before the `break`.
- **[S23] `stop()` uses a non-reentrant `Event.set()` in the signal path** — info, `daemon.py:995`. SIGINT and SIGTERM both call `stop()` → `Event.set()` (non-reentrant lock); a SIGTERM nesting inside a mid-`set()` SIGINT handler could self-deadlock the shutdown — the exact hazard the authors avoided for `request_reload()` with a plain bool. Shutdown-only, negligible probability. *Fix:* mirror `request_reload()` with a plain bool (optionally also set the Event for interruptible waits), or accept-and-document.

### AuthZ, audit & secret hygiene
- **[S13] Audit CSV is spreadsheet-formula-injectable via `target_template_id`** — low, `audit.py:404`. `export_csv` writes the `target` column raw, and `target_template_id` (agent-supplied, validated only non-empty) becomes that `target`, so a provision-tenant can plant a cell starting `=`/`+`/`-`/`@` that executes when the operator opens the exported CSV (CWE-1236). *Fix:* prefix-quote any cell starting with a formula char in `export_csv`, and/or enforce a slug charset `^[A-Za-z0-9._-]{1,96}$` at the boundary. *(Corroborated independently by the dashboard lens.)*
- **[S14] Signed-URL secrets stored unredacted in the audit (and logged on the operator path)** — low, `audit.py:61`. `redact()` masks by key-*name* denylist, so a presigned download URL's `X-Amz-Signature` under the key `url` is stored verbatim in `operator_audit.params`; on the operator build path `admin.py` also `log.info`s the raw url, and `logging_setup`'s query patterns don't match signature-style params. A time-limited credential lands in two secret-free-by-contract surfaces. *Fix:* canonicalize the audited/logged url to `scheme://host/path` (drop the query), or add value-level scrubs for `X-Amz-Signature`/`Signature`/`sig`.
- **[S15] LOG_LEVEL contract not honored; redaction filter not attached on dashboard/gateway** — low, `dashboard.py:2283`. `dashboard.main()` hardcodes `basicConfig(level=INFO)` (ignoring LOG_LEVEL *and* bypassing `logging_setup`'s `RedactionFilter`), `mcp_server.main()` configures no logging, and a standby daemon never applies the level — so an operator setting `LOG_LEVEL=DEBUG` on the very process they're debugging gets nothing, and the dashboard runs without the redaction defense-in-depth. *Fix:* resolve via `logging_setup.resolve_log_settings()` and call `configure_logging` at each entrypoint; apply the level in the standby loop; correct the 0022/CHANGELOG docs.
- **[S24] Cross-tenant read-verb docstrings overstate isolation** — info, `mcp_server.py:708`. `list_projects`/`queue_view`/`list_leases`/`list_templates` docstrings say "a token never sees other tenants," but an operator-scope token (`project_id=None`) legitimately receives the full cross-tenant view. Behavior is intended and safe (no *tenant* token can hold `project_id=None`); the description an agent sees is wrong. *Fix (docs-only):* note that a project-bound token sees only its tenant while a project-less operator token gets the cross-tenant view.

## 5. What held (anti-findings)

The review attacked the floor directly and these survived scrutiny — credit where the design is genuinely sound:

- **Ordered per-scope advisory locks.** `scope_keys()` sorts identically across `admit`/`promote_pinned`/`_reserve`; no debited scope was found unlocked or locked out of canonical order (the only residual is the astronomically-improbable S21 collision, which yields a *detected* deadlock, never a missed exclusion).
- **Derived-capacity model.** Capacity is computed as `limit − Σ leases in CAPACITY_STATES` at read time under the lock; no stored counter to drift, and RELEASING correctly holds capacity. No LEFT-JOIN capacity-multiplication path was found.
- **The vmid fence + the 0004 partial unique index.** The per-cluster double-stamp is refused (`VmidContended`, loser stays ADMITTED); the fence correctly stops a *sequential* stale destroy. The surviving teardown finding (S02) is a *timing window* around the fence, not a hole in the fence itself.
- **Guarded-CAS lifecycle.** `begin_provisioning`/`mark_active`/`release`/`claim_*` transitions are CAS-guarded; the queue-expiry-vs-promote race resolves to exactly one winner.
- **Transaction / rollback discipline across modules.** `bulk.py` per-id isolation, `daemon._promote` rollback-on-raise, `promote_pinned`'s try/except rollback+reraise all hold; the idempotency-before-capacity ordering is correct. The escapes found (S03, S18) are *error-surfacing* gaps, not poisoned-txn or lock-leak defects.
- **Auth tier matrix + ownership gates.** `tier_allows` fails closed, `bind_project` forces a reservation onto the token's own project, `lease_owned_by` returns a uniform `lease_forbidden`; no verb was found skipping `_authorize` or widening scope. The two authz findings are a *doc* overstatement (S24) and a *value-redaction* gap (S14), not a privilege-escalation or cross-tenant-action path.
- **The logging redaction filter — where it is actually attached.** `RedactionFilter` correctly scrubs tokens/DSNs/PVE credentials on the processes that install it; S15/S14 are about the *surfaces that miss it* (dashboard/gateway entrypoints, signature-style URL params), not a failure of the filter itself.

**Bottom line:** the machine that prevents double-allocation works.
