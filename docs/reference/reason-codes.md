# Reason codes

Every code br0kr can answer an agent with, what it means, and what to do about it. A code is an agent's only error
channel, and it arrives in one of these fields:

- `reason` on `request_lease` and `schedule_lease` (and per node in `schedule_lease`'s `tried` list), `set_quota`,
  `request_template_download`, and the operator tools;
- `error` when the call itself was refused (authorisation, tenancy, a malformed batch): `{"error": "<code>"}`;
- `hold_reason` and `released_reason` in `lease_status`: why an admitted lease is held, and why a lease ended;
- `blocked_reason` in `queue_status` and `queue_view`;
- `reason` in `migration_status`, and `error` in `replication_status`.

The first part is the vocabulary in [br0kr/reasons.py](../../br0kr/reasons.py).
`tests/unit/test_reason_codes_doc.py` fails when a code there has no row here, or a row here names a code that no
longer exists. The second part lists codes outside that vocabulary that an agent can still read back; the same test
fails when one of them stops appearing in the code.

## How to read a row

- **Where**: the tool and the field the code arrives in.
- **Meaning**: the exact condition.
- **Agent**: what an agent does next. It starts with one of these:
  - **Fix the ask**: the request is wrong; change it and send it again. A refused request creates no lease, so the
    same `idem_key` is free unless the row says otherwise (a pin refused after admission releases the lease and
    spends the key).
  - **Retry**: send the same ask again, now or later.
  - **Wait**: nothing to send; poll `lease_status` (and keep calling `renew_lease`).
  - **Do not retry**: the same ask fails the same way.
  - **Ask the operator**: only the operator can change what is in the way.
  - **Request a new lease**: the lease has ended; start again with a new `idem_key`.
  - **Nothing**: for information; no action needed.
- **Operator**: the lever that clears it (a setting, a dashboard card, an operator tool), or None.

A composite code is written `prefix:<detail>`: the prefix is fixed, the detail varies (an exit status, the reason
another check gave).

### The admission queue

A queued answer also carries `queue_position` and `next`. `queue_position` counts the queued requests across the whole queue (every node and project) that are older than yours: advisory, since the promoter is strict FIFO per scope. It is null when it is not known or the lease is no longer waiting (promoted, cancelled or expired before the count was read, or the read failed): check lease_status. `next` says what to do while you wait.

| Code | Where | Meaning | Agent | Operator |
|---|---|---|---|---|
| `queued` | `request_lease`, `schedule_lease` (`reason`, with queued=true); also the answer to a retry of a still-PENDING lease (idempotent=true) | The ask did not fit and queue=true parked it as a PENDING lease holding no capacity; the broker admits it in FIFO order. | Wait: poll lease_status until state leaves PENDING (ADMITTED, PROVISIONING or ACTIVE: yours; REJECTED: ended, read released_reason and ask again with a new idem_key); renew_lease within ttl_seconds to hold the spot (capped at max_wait_seconds); cancel_lease to give up. | None. To drain faster, free capacity or raise quotas; queue_view (operator token: every tenant) and fleet_stats show depth and oldest wait. |
| `queue_full` | `request_lease`, `schedule_lease` (`reason`, queued=false), only on a queue=true ask that did not fit | PENDING leases already reach the global queue_max (default 1000; 0 disables queueing) or your project's max_queued cap; nothing was reserved. | Retry later; cancel_lease queued requests you no longer need (queue_view lists them) to free your project's queue slots. | Raise queue_max (dashboard settings editor, BR0KR_QUEUE_MAX) or the project's max_queued (dashboard project card), or add capacity so the queue drains. |
| `no_reachable_instance_replicating` | `request_lease` only (`reason`, with queued=true); a retry of the parked lease answers `queued` | No reachable copy of template_id exists on this node yet, but a live replication is copying one there; queue=true parked the ask behind it. | Wait: poll lease_status until state leaves PENDING and renew_lease to hold the spot; if the copy fails the lease ends REJECTED with released_reason replication_failed, so ask again with a new idem_key. | None. Track the copy with replication_status; the ask parks only while the replication engine is enabled (replication_enabled). |

### Holds

| `replication_failed` | `lease_status`, `lease_statuses` (`released_reason`, state REJECTED) | The request was parked behind a template replication that ended FAILED (not already_present), and no READY copy or live enabled sibling job could serve it. | Ask the operator to fix and re-run the replication, then request a new lease. | Read the job's `error` (replication_status), fix it, wait out `replication_cooldown_seconds`, then run `replicate_template` again. |
| `placement_blocked:<hold_reason>` | `lease_status`, `lease_statuses` (`released_reason`) | Admitted, then held by the placement re-check for 60 consecutive daemon ticks (about five minutes), so the daemon released it; the suffix is the hold reason (see Holds above). | Ask the operator to fix the named hold, then request a new lease; retrying before the fix holds again. | Fix by hold reason: the Holds rows above, or the table under Br0krHeldLeasesReleased in alerts.md. |
| `cross_provision_detected` | `lease_status`, `lease_statuses` (`released_reason`) | The post-clone check found the boot disk on a different pool than placement chose; the daemon released the guest and quarantined that storage-node pair. | Request a new lease: placement now refuses that quarantined pair, so it lands elsewhere or is refused up front. | Run `verify_declarations`, fix the storage declaration, then clear the pair (`POST /api/storage/quarantine/clear`). |
| `data_disk_cross_provision_detected` | `lease_status`, `lease_statuses` (`released_reason`) | A data disk landed on a different pool than it was created on; the daemon released the guest and quarantined the expected pool on that node. | Request a new lease: placement now refuses that pool on that node. | Check that pool's `storage.cfg` entry on the node, fix the declaration, then clear the pair (`POST /api/storage/quarantine/clear`). |
| `network_unreachable_detected` | `lease_status`, `lease_statuses` (`released_reason`) | The post-clone net0 check found the node lacks the bridge declared for the template's logical network; the daemon released the guest and quarantined that pair. | Request a new lease: placement now refuses that node for this logical network. | Declare the node's real bridge (`POST /api/network/node`), then clear the pair (`POST /api/network/quarantine/clear`). |

### Migration reasons (`migrate_lease` and `migration_status`)

Why an operator's `migrate_lease` was refused, or why a cross-cluster migration of your lease stopped. A tenant sees
only its own lease's migrations, through `migration_status`.

| Code | Where | Meaning | Agent | Operator |
|---|---|---|---|---|
| `lease_not_active` | operator `migrate_lease` (`reason`); `migration_status` (`reason`, state ABORTED) | At reserve the lease was not ACTIVE with a vmid, or at actuation it was no longer live; nothing moved. | Nothing: check lease_status; the lease ended or never finished provisioning. | None. Request again with `migrate_lease` and a new `idem_key` once the lease is ACTIVE, if still wanted. |
| `storage_migration_unsupported` | operator `migrate_lease` (`reason`); `migration_status` (`reason`, state ABORTED) | The lease debits a storage pool; cross-cluster migration moves only compute-only leases, so nothing moved. | Nothing: your lease stays where it is; this lease cannot be migrated. | None. A storage-backed lease cannot be migrated yet (cross-cluster-migration.md). |
| `no_target_capacity:<admit_reason>` | `migration_status` (`reason`, state ABORTED) | admit() refused the target-capacity reservation; the suffix is admit's reason, such as `insufficient_node_cpu` or `node_cordoned`. The lease is untouched. | Nothing: your lease and guest stay on the source. | Free capacity on the target or uncordon it (`node_capacity`), then `migrate_lease` again with a new `idem_key`. |
| `reservation_lost` | `migration_status` (`reason`, state ABORTED) | The target reservation lease could not be renewed (it lapsed, e.g. TTL-reaped during a daemon outage), so the target slot was no longer held. | Nothing: your lease stays on the source. | Check daemon liveness (alerts.md Br0krDaemonStalled), then `migrate_lease` again with a new `idem_key`. |
| `source_changed` | `migration_status` (`reason`, state ABORTED) | The lease left the saga's recorded source node by another path before actuation, so this saga aborted without moving it. | Nothing: re-read lease_status for the lease's current node. | None. Request again with `migrate_lease` and a new `idem_key` from the new node, if still wanted. |
| `actuation:<verdict>` | `migration_status` (`reason`, state ABORTED) | No migrate task started: the source vmid held no guest (`gone`) or held another lease's guest (`fence_mismatch`). | Ask the operator: the ledger's vmid for your lease did not hold your guest; check lease_status and your VM. | Inspect the source node: `qm config <vmid>` should carry `br0kr-lease-<id>`; reconcile the lease by hand. |
| `migrate_task:<exitstatus>` | `migration_status` (`reason`, state ABORTED) | The PDM migrate task stopped with a definite non-OK exit status and the guest is not on the target; it stays on the source. | Nothing: your lease and guest stay on the source. | Read that migrate task's log on PDM, fix the cause, then `migrate_lease` again with a new `idem_key`. |
| `target_vmid_taken` | `migration_status` (`reason`, state ABORTED) | The guest landed on the target, but another live lease in that cluster already holds its new vmid, so the ledger flip was refused. | Ask the operator: your guest moved, but lease_status still names the source node and vmid. | Find the guest by fence `br0kr-lease-<id>` on the target cluster, resolve the vmid clash, and repair the lease row by hand. |
| `lease_gone_after_migrate` | `migration_status` (`reason`, state ABORTED) | The guest landed on the target, but the lease had left the source (released or expired) before commit; the moved guest is an orphan. | Nothing: the lease had already ended. | Confirm the orphan sweep destroyed the moved guest on the target (fence `br0kr-lease-<id>`); otherwise destroy it by hand. |
| `operator_cancelled` | `migration_status` (`reason`, state ABORTED) | An operator cancelled the saga with `cancel_migration` while it was REQUESTED or RESERVED; nothing moved. | Nothing: your lease and guest stay on the source. | None. |
| `same_cluster` | operator `migrate_lease` (`reason`) | The target node is in the lease's own cluster; br0kr brokers only cross-cluster moves (a same-cluster move is PVE's own migration). | Fix the ask: pick a target node in another cluster (list_nodes shows each node's cluster). | Move it within the cluster with PVE's own migration instead, if that is what is wanted. |
| `unknown_target_node` | operator `migrate_lease` (`reason`) | target_node names no node, or the node was deleted before the saga was recorded. | Fix the ask: use a node id from list_nodes. | Register the node (dashboard node create) if it should receive migrations. |
| `target_not_provisionable` | operator `migrate_lease` (`reason`) | The target node has no cluster, so the daemon could not run a guest there. | Fix the ask: pick a target node that belongs to a cluster. | Bind the node to its cluster on its dashboard node card. |
| `source_cluster_unknown` | operator `migrate_lease` (`reason`) | The lease has no recorded cluster (its cluster row was deleted), so br0kr cannot tell where its guest physically is. | Do not retry: this lease cannot be migrated. | Locate the guest by its fence tag `br0kr-lease-<id>` and repair the lease's cluster by hand, or release it. |
| `migration_in_progress` | operator `migrate_lease` (`reason`) | A live migration saga already moves this lease to a different target node (or one just ended between two reads). | Wait: follow the running saga with migration_status; ask again with a new idem_key once it has ended. | None; cancel_migration stops a saga that has not started copying. |

### Replication job reasons (`replication_status`)

`unknown_replication` is the `reason` of a miss; the rest arrive in `error` on a FAILED job. A tenant sees only jobs attributed to its own project.

| Code | Where | Meaning | Agent | Operator |
|---|---|---|---|---|
| `unknown_replication` | `replication_status` (`reason`, found false); also operator `cancel_replication`, `force_fail_replication` | No job has this id, or the job is attributed to another project; both answer identically on purpose. | Do not retry: check the `replication_id`; a tenant token sees only jobs attributed to its own project. | None. |
| `cancelled` | `replication_status` (`error`, job_state FAILED) | An operator cancelled the job with `cancel_replication` while it was REQUESTED; no guest was created. | Nothing: ask the operator if you still need the copy. | None. A re-request is allowed at once; the cooldown ignores cancels. |
| `operator_force_fail` | `replication_status` (`error`, job_state FAILED) | An operator forced the job FAILED with `force_fail_replication`, without teardown; with a note, the error reads `operator_force_fail:<note>`. | Ask the operator whether a new copy is coming before you queue behind this template again. | If the force returned a `vmid`, remove guest `br0kr-repl-<id>`; the leaked-guest reclaim destroys it once its node is served. |
| `job_unbound` | `replication_status` (`error`, job_state FAILED) | Defensive: the job reached the copy step without a target node or declared size, which a REQUESTED job always has. | Ask the operator to request the replication again. | Run `replicate_template` again; report a bug if it repeats. |
| `target_storage_insufficient:<admit_reason>` | `replication_status` (`error`, job_state FAILED) | admit() refused the target pool byte reservation; the suffix is admit's reason, such as `insufficient_storage`. | Ask the operator to free space on the target pool or choose another pool. | Free space on the target pool or pick another (`list_storage`), wait out the cooldown, then `replicate_template` again. |
| `already_present` | `replication_status` (`error`, job_state FAILED) | A live instance already holds this exact template and target slot, so the job had nothing to copy. | Nothing: a request queued behind it is admitted on a later tick. | None. |
| `reservation_lost` | `replication_status` (`error`, job_state FAILED) | The job's target byte reservation could not be renewed (it lapsed), so the copy was torn down. | Ask the operator to request the replication again. | Check daemon liveness (alerts.md Br0krDaemonStalled), then `replicate_template` again after the cooldown. |
| `source_or_target_vanished` | `replication_status` (`error`, job_state FAILED) | The source instance's vmid or the target pool's PVE name is gone; for rebuild_source, the template's recorded source URL or checksum. | Ask the operator to restore the template or pool, then re-request. | Check the source instance (`list_template_instances`) and target pool (`list_storage`); restore or pick another, then re-request. |
| `source_fence_lingering` | `replication_status` (`error`, job_state FAILED) | The source template still carries a `br0kr-repl-<id>` fence from an earlier replica whose finalize strip failed, so cloning it was refused. | Ask the operator to clear the stale fence tag, then re-request. | Remove the `br0kr-repl-<id>` tag from the source template (the finalize-retry step also strips it), then re-request. |
| `source_unmarked` | `replication_status` (`error`, job_state FAILED) | The source template lacks the `br0kr-template` marker tag, so cloning it was refused before any guest was created. | Ask the operator to tag the template, then re-request. | Tag the source template `br0kr-template` (vm-access.md §2, step 4), then `replicate_template` again. |
| `clone_failed:<exitstatus>` | `replication_status` (`error`, job_state FAILED) | PVE's full-clone task onto the target pool stopped with a non-OK exit status; the partial copy was destroyed. | Ask the operator to fix the clone cause, then re-request. | Read that clone task's log in PVE, fix the cause (storage, permissions), wait out the cooldown, then re-request. |
| `fence_mismatch_after_clone` | `replication_status` (`error`, job_state FAILED) | After the clone, the guest at the job's vmid was not this job's clone (wrong name or fence), so it was left untouched. | Ask the operator to inspect the vmid, then re-request. | Inspect the job's `vmid` with `qm config`; it belongs to someone else, so do not destroy it blindly. |
| `clone_vanished` | `replication_status` (`error`, job_state FAILED) | The cloned guest was gone before its fence could be stamped; nothing was left to destroy. | Ask the operator to request the replication again. | Check PVE for a concurrent delete on that vmid, then `replicate_template` again. |
| `landed_wrong_pool:<pve_pool>` | `replication_status` (`error`, job_state FAILED) | The copy's boot disk landed on a different PVE pool (the suffix) than the target; the pair was quarantined and the copy destroyed. | Ask the operator to fix the pool declaration, then re-request. | Run `verify_declarations`, fix the target pool declaration, clear the pair (`POST /api/storage/quarantine/clear`), then re-request. |
| `source_hand_modified` | `replication_status` (`error`, job_state FAILED); also an operator `replicate_template` refusal | A rebuild_source job found the template flagged `source_dirty` (hand-modified) at actuation, and the request was not forced. | Ask the operator whether to force the rebuild or use `clone_shared`. | Re-request with `force_source_dirty=true` (audited) or with `mechanism=clone_shared`. |
| `rebuild_acl_denied` | `replication_status` (`error`, job_state FAILED) | PVE answered 401 or 403 to the rebuild's download or create-and-import call: the broker's PVE token lacks a privilege. | Ask the operator to grant the missing PVE privilege, then re-request. | Grant `Datastore.AllocateTemplate` on the pool and `Sys.AccessNetwork` on the node (download), plus `VM.Allocate` and pool Datastore rights (import). |
| `rebuild_download_failed:<exitstatus>` | `replication_status` (`error`, job_state FAILED) | PVE's download of the template's recorded source image stopped non-OK; the suffix is the task's exit status, redacted. | Ask the operator to fix the image source, then re-request. | Fix the source URL or checksum (or the node's reach to the mirror), wait out the cooldown, then re-request. |
| `rebuild_import_failed:<exitstatus>` | `replication_status` (`error`, job_state FAILED) | PVE's create-and-import task for the rebuilt guest stopped with a non-OK exit status. | Ask the operator to fix the import cause, then re-request. | Read the import task's log in PVE, fix the cause (pool content, space, permissions), then re-request after the cooldown. |
| `fence_mismatch_after_rebuild` | `replication_status` (`error`, job_state FAILED) | The guest at the job's vmid was not this job's rebuild (wrong name or fence), so it was left untouched. | Ask the operator to inspect the vmid, then re-request. | Inspect the job's `vmid` with `qm config`; it belongs to someone else, so do not destroy it blindly. |
| `rebuild_vanished` | `replication_status` (`error`, job_state FAILED) | The rebuilt guest was gone before its fence could be verified; nothing was left to destroy. | Ask the operator to request the replication again. | Check PVE for a concurrent delete on that vmid; the downloaded source file may remain on the pool. Re-request. |
| `rebuild_no_boot_disk` | `replication_status` (`error`, job_state FAILED) | The imported guest had no parseable boot disk, so the job failed closed rather than publish a diskless template. | Ask the operator to check the source image, then re-request. | Confirm the source URL serves a bootable disk image PVE can import, then re-request. |
| `fence_mismatch_at_convert` | `replication_status` (`error`, job_state FAILED) | Just before conversion to a template, the vmid no longer carried this job's fence, so it was left untouched. | Ask the operator to inspect the vmid, then re-request. | Inspect the job's `vmid` with `qm config`; it changed hands, so do not destroy it blindly. |
| `convert_failed:<exitstatus>` | `replication_status` (`error`, job_state FAILED) | PVE's convert-to-template task stopped with a non-OK exit status; the copy was destroyed. | Ask the operator to fix the convert cause, then re-request. | Read the convert task's log in PVE, fix the cause, then re-request after the cooldown. |
| `lost_ready_cas` | `replication_status` (`error`, job_state FAILED) | Marking the job READY failed: the job left CONVERTING or its REPLICATING twin instance was retired first; the copy was destroyed. | Ask the operator to request the replication again. | Check whether someone retired the twin instance (`/api/instance/retire`), then re-request. |
| `reclaimed:<cause>` | `replication_status` (`error`, job_state FAILED) | The leader reclaimed the job and destroyed its guest: `stale` when it made no progress write for BR0KR_REPL_STALE_SECONDS (default 7200 s), `wall_time_exceeded` when it was not READY within 4 times that of copy start. | Ask the operator to request the replication again. | For stale, look for `step raised` lines on the job in the daemon log; for wall time, a wedged PVE task (or raise BR0KR_REPL_STALE_SECONDS for slow copies). Then re-request. |
